# T3.10 模板版本化 v1

> Sprint: Phase 3 · 状态: 未开始 · 规模: S · 前置: T3.1–T3.9 全部

## 目标

给 app-content 模板一个正式身份：`TEMPLATE.yaml` 记版本与元数据，registry 回填 innate-wip 的出身记录。模板从此可被引用（`templateVersion`）、可被比较（doctor 报"落后 N 版"）、可被升级（显式动作）。

## 背景与动机

总方案 §9：模板 = 基座成熟模式的快照，**带版本**。两个方向的同步都必须显式——基座演进不自动改模板，模板升版不自动改存量 app。`templateVersion` 就是记录落差的字段，而它的前提是模板自身有版本。

## 工作项

1. `factory/templates/app-content/TEMPLATE.yaml`：

   ```yaml
   name: app-content
   version: v1
   description: 内容型站：Next static export + plugin registry + @innate/ui（verdaccio）
   requires:
     "@innate/ui": ">=0.1.1"        # 与 T3.7 固化版本一致
   placeholders: [app-name, app-title, app-desc, base-path, scope]   # 与 T3.4 终稿一致
   changelog:
     - v1 (2026-09): 从 innate-wip 固化（见 docs/innate-factory/phase-3/T3.2 清单终稿）
   ```
   注意：TEMPLATE.yaml 本身**不参与实例化复制**（Phase 4 引擎排除项），也避免其中的 `{{…}}` 字样干扰占位符断言——placeholders 用裸字段名列表，不写花括号。
2. 版本语义写进 `factory/templates/README.md`：
   - 模板内容变更 → 模板 PR 里显式 bump version + changelog 一行
   - 存量 app 不自动跟版；升级是显式动作（对照 diff + 手工合并），未来可长 `innate template upgrade`（不在当前里程碑）
3. registry 回填（innate-workspace 仓 `registry/apps.yaml`）：

   ```yaml
   - name: innate-wip
     kind: core
     template: app-content
     templateVersion: v1     # 出身记录：由 v1 固化而来（wip 是源，不是产物，此字段表血缘）
   ```
4. Sprint 3 收尾：把 phase-3/README.md 的 DoD 勾完，状态行更新。

## 产物

`TEMPLATE.yaml` + templates/README 版本语义 + registry 回填 + Sprint DoD 勾选。

## 验收标准

- [ ] TEMPLATE.yaml 字段完整，requires 与模板实际依赖一致
- [ ] 冒烟 CI 的实例化路径确认排除 TEMPLATE.yaml（或其内容不影响断言）
- [ ] registry/apps.yaml 中 innate-wip 带 `template: app-content, templateVersion: v1`，且随后跑一遍 scan（EXTRA_KEYS 保留机制）该字段不丢
- [ ] phase-3 README DoD 全勾

## 风险与注意

- scan.py 的 EXTRA_KEYS 合并规则（"kind / template / deploy 等手工字段在 read→merge→write 往返中保留"）是回填安全的前提——Phase 1 已验证过 diff 为零，此处再确认 template/templateVersion 在 EXTRA_KEYS 白名单内；不在就先补白名单再回填。
