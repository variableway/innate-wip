# T3.9 模板冒烟 CI

> Sprint: Phase 3 · 状态: 未开始 · 规模: M · 前置: T3.4 · T3.7

## 目标

新增 `.github/workflows/template-smoke.yml`：模板有变更时 + 每周定时，把全部模板实例化一遍并构建。模板腐烂在这里被拦住，而不是在新 app 生成时（总方案 §5 防腐第 1 条）。

## 背景与动机

模板是"生成即可用"承诺的源头，但模板依赖（`@innate/ui`、Next 版本）会随时间腐烂——本地绿不代表三周后还绿。冒烟 CI 是唯一能持续证明模板活着的机制。

**核心难点**：模板依赖私有 verdaccio 的 `@innate/ui`，而 GitHub Actions 跑不到本机 verdaccio。解法：**workflow 内自起 verdaccio service 容器，并从 fe-base 现场发布 ui**，再实例化构建。这条链路同时也是 Phase 2 发布流程的持续验证，一石二鸟。

## 工作项

1. workflow 触发器：

   ```yaml
   on:
     push: { paths: ['factory/templates/**'] }
     pull_request: { paths: ['factory/templates/**'] }
     schedule: [{ cron: '0 3 * * 1' }]   # 每周一 03:00
   ```
2. matrix：模板清单。v1 手写 `[app-content]`；模板 ≥ 3 个后改为动态发现 `factory/templates/*/TEMPLATE.yaml`。
3. 单模板 job 步骤：
   1. checkout innate-workspace
   2. 起 verdaccio service 容器（`services: verdaccio: image: verdaccio/verdaccio`，端口 4873）
   3. checkout `base/innate-fe-base`，`packages/ui` 执行 `pnpm publish --registry http://localhost:4873`（本地无认证形态）
   4. **实例化**：v1 用脚本把占位符替换为冒烟值（`app-name=smoke-app` 等）到临时目录；**Phase 4 完成后切换为调用 `factory/scaffold/new_app.py --dry-build`**（冒烟与真实生成路径合一，避免两套实例化逻辑漂移）
   5. `pnpm install && pnpm build`
   6. 断言：`grep -r '{{' <target>` 为零；`dist/` 存在且首页 html 非空；实例化副本内 skill 目录名正确（T3.6）
4. 失败通知：v1 靠 GitHub 默认邮件；后续可挂进 dispatch 看板（Phase 5）。

## 产物

`.github/workflows/template-smoke.yml`（innate-workspace 仓）。

## 验收标准

- [ ] 新增 workflow 的 PR 上跑绿（真实 verdaccio 容器 + fe-base 发布 + 构建）
- [ ] 周触发 schedule 配置生效（下周一可查首次运行）
- [ ] 一次性实验：故意在模板里留一个未替换占位符 → CI 红；复原 → 绿（证明断言真的在工作）

## 风险与注意

- fe-base 主干当天的状态决定冒烟成败——若 fe-base 自身坏了，冒烟会红但根因不在模板。缓解：发布步骤失败时的错误信息明确写"fe-base ui 发布失败，先修 fe-base"。
- pnpm 缓存能把 install 压到分钟级，workflow 里记得用 `actions/setup-pnpm` + cache。
- schedule 触发只跑默认分支——模板冒烟的意义正是保默认分支健康，符合预期。
