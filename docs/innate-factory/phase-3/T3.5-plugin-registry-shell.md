# T3.5 plugin registry 空壳化

> Sprint: Phase 3 · 状态: 未开始 · 规模: S · 前置: T3.3

## 目标

把 wip 的 build-time plugin registry（现为 making / cheatsheets / awesome 三个硬编码插件）固化为模板内的**空壳**：零插件也能 build，插一个示例插件就能出现在导航。

## 背景与动机

模板不应替用户预选内容模块——那是 preset 的职责。但插件机制本身（manifest / registry / feature flag）是 content 站骨架的一部分，且是双轨方案（route | iframe）的宿主侧落点。空壳 = 机制保留、内容清零。

wip 现状（`apps/web/lib/plugins/`）：`registry.ts`（三个插件 + `getEnabledPlugins` / `getPluginById` / `getEnabledHomeTiles`）、`types.ts`（`SitePlugin`，`loadMode: "route" | "iframe"`）、`icons.tsx`。`lib/site-features.ts` 按 flag 控制显隐。

## 工作项

1. 模板内 `registry.ts`：`plugins: []` + 顶部注释给一个 route 示例与一个 iframe 示例（注释形态，不启用）；三个 helper 函数原样保留。
2. `types.ts` / `icons.tsx` 原样保留（双轨 manifest schema 零改动的承诺来自 plugin-dual-track.md §0）。
3. `site-features.ts` 收敛：只留 content / feed（按 T3.2 决策项 C）+ 注释说明 plugin-mode 玩法与 docs/solution 链接（生成后的 app 内此链接指向 wip 仓，注明可删）。
4. wip 里因空壳化而失去引用的组件（如 home tiles 渲染、sidebar 分组渲染）保留渲染逻辑、吃空数组——空数组下 UI 不崩即可（首页 tiles 区为空是合理形态）。
5. 与 `registry/plugins.yaml` 的边界写进模板 README：plugins.yaml 记的是**可装件**（跨 app 的插件清单），宿主 `lib/plugins/registry.ts` 记的是**本 app 装了什么**；模板生成时 plugins.yaml 不产生条目，首个插件出现时才登记。

## 产物

模板内空壳化后的 `lib/plugins/` + 收敛后的 `site-features.ts`。

## 验收标准

- [ ] 零插件状态下 build 绿，首页 / 导航不报错不显示空区块
- [ ] 临时加一个 route 示例插件（验完删）：nav 分组、home tile、路由页三处都能出现
- [ ] `SitePlugin` 类型与 wip 逐字段一致（宿主契约不因固化而漂移）

## 风险与注意

- 空数组边界（`getEnabledHomeTiles()` 返回空、sidebar 无分组）要实测 UI，别只看 build 绿。
- 不要顺手把 registry 改成"自动发现包依赖"（dual-track §1 优化点里的 `registry.gen.ts`）——那是远期优化，v1 空壳保持手写注册的简单形态。
