# T3.1 factory/ 目录骨架

> Sprint: Phase 3 · 状态: 未开始 · 规模: S · 前置: 无（但需 Phase 0 的 gitignore 例外已生效）

## 目标

在 innate-workspace 根建立 `factory/` 四目录骨架，职责边界写进各目录 README。后续所有模板 / 生成器 / 接线工作都落在这个结构里，不再讨论"放哪"。

## 背景与动机

总方案 §1 规定 `factory/` 由 templates / presets / scaffold / hooks 四件构成。先立骨架再固化模板，避免 T3.3 固化时"边造边定结构"。

## 工作项

1. `mkdir -p factory/{templates,presets,scaffold,hooks}`
2. 写 `factory/README.md`：四目录职责 + 三条防腐原则（模板即项目 / 目录为源 / 生成即可用，引用总方案 §5）
3. 各子目录 README（简短即可）：
   - `templates/`：真实可构建工程，一模板一目录，`TEMPLATE.yaml` 记版本（T3.10）
   - `presets/`：模板组合预设——变体用 preset 表达，不膨胀模板（§5 第 4 条）
   - `scaffold/`：生成器（Phase 4 python 起步，M2 由 innate-cli 收编）
   - `hooks/`：生成后接线（registry 登记 / CI 生成 / 部署配置）
4. 验证 Phase 0 预铺的 `!factory/templates/**` gitignore 例外：临时放一个测试 png 进 `templates/`，`git check-ignore -v` 确认不被忽略，随后删除测试文件

## 产物

`factory/` 四目录 + README ×5。

## 验收标准

- [ ] 目录结构与总方案 §1 一致
- [ ] `git status` 可见全部新增文件；二进制例外验证通过
- [ ] 每个 README 说清"什么放这里、什么不放"

## 风险与注意

- `scaffold/` 与 `hooks/` 职责易混淆。边界写死：**scaffold 负责"生成那一刻"（复制模板、替换占位符、git init），hooks 负责"生成之后"（registry 登记、CI 接线、部署配置）**。Phase 4 实现时如果发现 new_app.py 内联了登记逻辑，那是 hooks 的职责被内联了——允许（单人效率优先），但 README 里注明。
