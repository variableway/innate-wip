# T4.8 首跑验收：真实小 app

> Sprint: Phase 4 · 状态: 未开始 · 规模: M · 前置: T4.1–T4.7 全部

## 目标

factory 的定义性时刻：用 `new_app.py` 生成一个**真实**小 app（不是 demo-throwaway），全链验收，归档验收记录与摩擦清单。后者是 Phase 5（Go 收编）最重要的需求输入。

## 背景与动机

总方案 §10 Phase 4 验收原文："用 factory 生成一个真实小 app，构建绿、registry 有记录、看板 issue 建好"。"真实"是关键词——玩具 app 测不出真问题（真实 app 会有真实的 basePath / 真实的远程仓 / 真实的后续迭代），而 factory 的承诺是对真实工作流的。

## 工作项

1. **选型**：从 backlog 挑一个真实小需求（建议形态：link/notes 型微型内容站，或一个已想做的 tooling 小站）。选型标准：你会继续维护它；部署目标明确（最好 pages，链路最短）。
2. **全链执行**（记录每步耗时）：

   ```bash
   python3 factory/scaffold/new_app.py <name> --category <c> --deploy pages
   ```
   预期一次走完：实例化 → git init → registry 登记 → 构建绿 → deploy 接线 → 远程仓（或降级三步执行）。
3. **看板 issue**（§7 闭环的最小预演）：

   ```bash
   gh issue create -t "app: <name> 落地" -l factory-generated -b "由 innate-factory app-content@v1 生成，验收记录见 <链接>"
   ```
4. **部署验证**（若选 pages）：push 后 workflow 绿、线上可访问、basePath 正确。
5. **归档**：本目录新增 `acceptance.md`：命令回放、各步耗时、产物链接（仓 / 线上址 / issue 号）、环境版本（node/pnpm/git/gh）。
6. **摩擦清单**：过程中每一个"卡了一下 / 要查文档 / 报错不清"瞬间记一条 → 转成 issue（label `factory-friction`），Phase 5 逐条消化。
7. **冒烟合流**：把 T3.9 的实例化步骤切到 `new_app.py`（README DoD 项），发 PR 验证 CI 绿。
8. Sprint 收尾：phase-4 README DoD 全勾，状态更新。

## 产物

真实 app 仓 + `acceptance.md` + 摩擦 issue 列表 + 冒烟 CI 合流 PR。

## 验收标准

- [ ] 真实 app：build 绿 / registry 有记录（scan 后 diff 零）/ issue 建好 / （选做）线上可访问
- [ ] acceptance.md 完整（含环境版本——跨机器复现的凭据）
- [ ] 摩擦清单 ≥ 1 条（诚实记录；零摩擦基本说明没认真用）
- [ ] 冒烟 CI 调用 new_app.py 后绿

## 风险与注意

- 选型冲动是大坑：选个"顺手做个大站"的需求会让 Sprint 4 收不了口。**小而真实**，宁可简单。
- 验收中发现生成器缺陷 → 回对应任务卡修复重跑，不要在验收现场手工补生成物（那等于掩盖缺陷，下一个用户还会踩）。
