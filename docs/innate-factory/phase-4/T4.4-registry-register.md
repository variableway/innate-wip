# T4.4 registry/apps.yaml 自动登记

> Sprint: Phase 4 · 状态: 未开始 · 规模: M · 前置: T4.2

## 目标

生成成功后自动把新 app 追加进 `registry/apps.yaml`（总方案 §3 第 4 步），并与 scan 的"目录为源"哲学无冲突共存。

## 背景与动机

总方案 §5 第 2 条：**目录为源**——registry 跟随磁盘现实，factory 只在"新建"时写 registry，之后 scan 维护。两者不打架的前提是登记条目能活过 scan 的 read→merge→write 往返：scan.py 的合并规则按 path 匹配保 name/desc、按 URL 匹配自动处理搬移、EXTRA_KEYS（kind/template/deploy 等手工字段）显式保留。生成的条目只要字段齐、path 真、repo URL 准，scan 只会确认它而不会改写它。

## 工作项

1. 追加条目（总方案 §2 schema）：

   ```yaml
   - name: <name>
     kind: satellite
     template: app-content
     templateVersion: v1
     path: innate-apps/<category>/<name>
     repo: <远程仓 URL，T4.5 建仓后回填；未建则省略>
     deploy: [<按 --deploy，none 则省略>]
     desc: <--desc 或默认>
   ```
2. 写入方式：沿用 scan.py 的 YAML 读写与排序约定（追加到对应 category 分组，保持文件既有注释结构不丢）。
3. 回填时机：repo URL 在 T4.5 建仓成功后补写（同一次运行内）。
4. 共存验证（本卡核心验收）：生成后立即 `python3 scripts/scan-innate-apps.py`，git diff 该条目应为零（scan 承认现实，不改一字）。
5. 失败语义：registry 写入失败（文件冲突 / 格式异常）→ 整体生成标记失败并提示手工补登记，不静默跳过。

## 产物

`new_app.py` 的 `registry_register` 步骤。

## 验收标准

- [ ] 新条目字段与 §2 schema 一致，落在正确 category 分组
- [ ] 生成后跑 scan：该条目 diff 为零（desc / kind / template / templateVersion / deploy 全保留）
- [ ] 同名拒绝（T4.1 校验）与登记幂等（失败重跑不产生重复条目）
- [ ] registry.yaml（外部 skills 仓那份，根目录）不受影响

## 风险与注意

- **先有目录后有登记**的顺序不能反：scan 的合并规则以磁盘为准，登记早于目录生成会被下一次 scan 当幽灵条目清除。流程编排（T4.1）已保证 instantiate 在前，此卡在验收里固化这个顺序约束。
- path 必须与生成落位（T4.5）严格一致，否则 scan 触发"repo move"分支改写 path——虽然能自愈，但 diff 不为零就是共存契约破了。
