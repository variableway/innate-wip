# T4.5 远程仓与落位

> Sprint: Phase 4 · 状态: 未开始 · 规模: M · 前置: T4.3（先有 commit 才有 push）

## 目标

生成物落位 `innate-apps/<category>/<name>/`（与 registry path 一致），可选创建 GitHub 远程仓并推送；`gh` 不可用时优雅降级，绝不拖垮整体流程。

## 背景与动机

总方案 §3 第 3 步（git init + gh repo create 可选）与"不吸收 innate-apps"决策：app 仓物理独立，workspace 只索引。落位即 registry path，这是 scan 共存契约（T4.4）的物理基础。降级设计的原因：远程创建依赖网络 / gh 登录态 / 配额，属"锦上添花"环节，不该让本地生成失败。

## 工作项

1. 落位：T4.2 的 instantiate 直接生成到 `innate-apps/<category>/<name>/`（不是先生成到临时目录再搬——搬移会破坏 T4.4 的先目录后登记时序与 T4.3 的 git 仓内路径）。
2. 远程创建（默认尝试，`--no-remote` 跳过）：

   ```bash
   gh repo create <owner>/<name> --private --source <path> --push
   ```

   默认 **private**（个人仓库安全缺省）；成功后把 repo URL 回填 registry（T4.4 步骤 3）。
3. 降级路径（gh 缺失 / 未登录 / 网络失败）：不 fail 整体，summary 打印手工三步：

   ```
   1. 网页建仓 https://github.com/new（名字建议：<name>）
   2. git -C <path> remote add origin git@github.com:<owner>/<name>.git
   3. git -C <path> push -u origin main
   ```
4. owner 取 `gh api user` 失败时从 registry 现有 variableway 条目推断并标注"推断值，请确认"。

## 产物

`new_app.py` 的 `remote_setup` 步骤 + 落位约定。

## 验收标准

- [ ] 有 gh 且登录：远程仓存在（private）、已推送 main、registry 条目带 repo URL
- [ ] 无 gh（PATH 摘除模拟）：整体退出码 0，summary 含手工三步，registry 条目省略 repo 字段
- [ ] 落位路径 = registry path（字符串级一致）
- [ ] innate-workspace 仓的 `git status` 不把新 app 目录当未跟踪内容（innate-apps/ 忽略规则生效）

## 风险与注意

- `gh repo create` 的 `--source --push` 一步到位但失败模式多（重名 409、SSH key 未配）：失败信息要区分"仓已建但推送失败"（提示手工 push 即可）与"仓没建成"（走降级三步），不要笼统报错。
- category 合法集合与 registry 现有分组（content / tooling / github-profile / base）对齐，新 category 需人工确认——v1 只开放三个既有的，避免 scan 分组注释结构被随意扩张。
