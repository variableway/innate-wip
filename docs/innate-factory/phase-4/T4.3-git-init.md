# T4.3 git init + 首 commit

> Sprint: Phase 4 · 状态: 未开始 · 规模: S · 前置: T4.2

## 目标

生成目录即刻成为独立 git 仓：`git init -b main` + 单条首 commit，commit 信息内嵌模板版本。生成即版本化、即血缘可溯。

## 背景与动机

总方案 §3 第 3 步。app 仓物理独立（`innate-apps/` 被 workspace 忽略、嵌套 git 不冲突——innate-workspace 现有模式如此，registry 里每个条目都是独立 clone）。首 commit 是 templateVersion 的第二个记录点（第一个在 registry，T4.4）——将来排查"这个 app 是从哪个模板版长出来的"时，`git log` 第一条就有答案。

## 工作项

1. `git init -b main`（目标目录内；`-b` 需 git ≥ 2.28，不满足则 `git init` + `git symbolic-ref HEAD refs/heads/main`）。
2. `git add -A` + 首 commit，信息模板：

   ```
   chore: scaffolded from app-content@v1 by innate-factory

   Template: factory/templates/app-content (v1)
   Placeholder values: name=<name>, base-path=<base-path>
   ```
3. 失败处理：git 缺失 / user.name / user.email 未配 → 报错并打印配置指引；`--no-git` 跳过本步（T4.5 远程步随之跳过并提示）。
4. commit 身份沿用全局 git config，不做仓库级覆盖。

## 产物

`new_app.py` 的 `git_init` 步骤。

## 验收标准

- [ ] 生成目录 `git log --oneline` 恰一条 commit，分支 main，`git status` 干净
- [ ] commit 信息含模板名 + 版本 + 占位符关键值
- [ ] git 未配置身份时错误信息可行动（含两条配置命令）
- [ ] `--no-git` 时目录正常存在，summary 提示后续手工 git init

## 风险与注意

- pnpm 的 `pnpm-lock.yaml` 在首 commit 前生成（T4.6 的 install 产物会写入锁）——顺序上 install/build 在 git_init 之后，锁文件会是**工作区未提交变更**。选择：v1 接受（用户首个自然动作就是提交锁文件），summary 里提示"首次 install 生成的 lockfile 记得 commit"。备选（更干净）：把 build_verify 提到 git_init 之前、commit 放最后——若采备选，改 T4.1 流程编排并同步本卡。**默认走 v1 接受**，避免流程重构。
