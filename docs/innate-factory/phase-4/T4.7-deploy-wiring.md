# T4.7 deploy 接线

> Sprint: Phase 4 · 状态: 未开始 · 规模: S · 前置: T4.2 · T3.8（桩）

## 目标

按 `--deploy pages|cloudflare|none` 完成部署接线：启用对应 workflow 桩、删掉未选桩、登记 `registry/deploy.yaml`。一个 app 可登记多个部署目标（总方案 §2："代码单元 ≠ 部署单元"）在此起步。

## 背景与动机

T3.8 的桩是"两份都带"，本卡决定"留哪份"。v1 的 `--deploy` 单值（pages / cloudflare / none）；多目标（`--deploy pages --deploy cloudflare`）留到真实需求出现——schema（deploy.yaml 的列表形态）已兼容，只是 CLI 参数暂单值。

## 工作项

1. `--deploy pages`：保留 `deploy-pages.yml`（占位符已被 T4.2 替换，直接可用），删除 `deploy-cloudflare.yml`；`registry/deploy.yaml` 追加：

   ```yaml
   - app: <name>
     targets: [pages]
   ```
2. `--deploy cloudflare`：同理；summary 打印手工项（Cloudflare 项目创建 + API token secret 配置，对应桩内 `TODO(innate-factory)` 注释）。
3. `--deploy none`（默认）：删除两个桩（生成物干净），不写 deploy.yaml 条目；summary 提示"以后要部署：手工加回 workflow 桩或重跑带 --deploy 的生成（同目录会被拒，建议手工）"。
4. deploy.yaml 写入遵循 T4.4 同款纪律：结构化追加、不破坏既有注释、失败即整体失败不静默。

## 产物

`new_app.py` 的 `deploy_wire` 步骤。

## 验收标准

- [ ] `--deploy pages`：生成物只含 pages workflow，actionlint 通过；deploy.yaml 有对应条目
- [ ] `--deploy cloudflare`：含手工项提示的 summary；条目正确
- [ ] `--deploy none`：零 workflow 残留，deploy.yaml 无条目
- [ ] scan 跑后 deploy.yaml 不受影响（scan 不管理此文件，验证仅是防误伤）

## 风险与注意

- pages 形态的 `{{base-path}}` 在 T4.2 已替换；但 GitHub Pages 的 basePath 实际取决于**部署仓的仓库名**（用户网页建仓时可能改名）——summary 里提示"若远程仓与 app-name 不同名，需改 next.config 的 basePath 与 workflow 内路径"。
- 删桩不可逆（对这次生成而言）——但模板永远有两份原件，恢复成本低，不需要做"回收站"机制。
