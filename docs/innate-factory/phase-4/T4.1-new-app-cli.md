# T4.1 new_app.py CLI 设计与骨架

> Sprint: Phase 4 · 状态: 未开始 · 规模: S · 前置: T3.4（占位符规范）

## 目标

定死 `factory/scaffold/new_app.py` 的参数模型与流程编排，实现骨架（validate + 流程框架 + dry-run），各步骤先为占位函数，由 T4.2–T4.7 逐个填实。

## 背景与动机

总方案 §3 的 `innate new app` 流程有六步，python 版是它在 M1 的肉身。参数模型先行的理由：T4.2–T4.7 各卡只管实现自己的步骤函数，接口不再漂移；冒烟 CI（T3.9）也按此调用。

**依赖策略**：与现有 scan 家族一致——纯 python3 stdlib，零第三方依赖（scan.py / scan-innate-apps.py / clone-innate.py 已核实只用 argparse / subprocess / pathlib）。registry 读写如需结构化，参照 scan.py 的现有做法（手写受限 YAML 读写 + EXTRA_KEYS 往返），不引入 pyyaml。

## 工作项

1. CLI 签名（argparse）：

   ```
   new_app.py <name>
     [--template app-content]          # 默认唯一模板
     [--category content|tooling|github-profile]   # 默认 content，决定 innate-apps/<category>/ 落位
     [--deploy pages|cloudflare|none]  # 默认 none（T4.7）
     [--title] [--desc]                # 缺省从 name 派生（T3.4 默认值规则）
     [--base-path]                     # 缺省 /<name>
     [--registry-url]                  # 缺省 http://localhost:4873，改写 .npmrc（T3.7）
     [--no-git] [--no-remote] [--keep] [--dry-run] [--yes]
   ```
2. 校验规则：name 合法 kebab-case；不与 `registry/apps.yaml` 现有 name 冲突；目标目录不存在或为空。
3. 流程编排（每个步骤 = 独立函数 + 独立可失败）：

   ```
   validate → instantiate → git_init → registry_register → build_verify → deploy_wire → remote_setup → summary
   ```
4. `--dry-run`：打印完整计划（目标路径、占位符替换表、registry 追加条目预览、将启用的 workflow），零落盘。
5. `summary` 输出契约：创建路径 / 模板版本 / 构建耗时 / registry 变更 / 下一步手把手（≤3 条）。

## 产物

`factory/scaffold/new_app.py`（骨架 + dry-run 可用）。

## 验收标准

- [ ] `--help` 完整；`--dry-run` 输出计划且磁盘无变化
- [ ] 非法 name / 重名 / 目标非空三类输入被清晰拒绝
- [ ] 各步骤函数有 docstring 声明由哪张卡填实

## 风险与注意

- 参数面克制：v1 不加 `--in-core` / `--preset`（README 不做清单已声明），骨架函数留锚点即可。
- 步骤间通过显式 context 对象传递（目标路径 / 替换表 / registry 条目），避免全局态——为 Phase 5 Go 移植留清晰边界。
