# T5.5 innate doctor（健康巡检）

> Sprint: Phase 5（W2）· 状态: 未开始 · 规模: M · 前置: T5.2（registry 层）· T5.4（npm 查询）
> 对应里程碑 M3

## 目标

`innate doctor` 一条命令回答"我的 factory 生态健康吗"：逐 app / 逐基座 / 逐表检查一致性，输出表格 + 机器可读退出码，可进 CI 也可日常巡检。

## 背景与动机

总方案 §4：doctor 报告"注册一致 / 构建绿 / 依赖过期"。§9 又加了一项关键职责：**templateVersion 落差报告**（"落后 N 版"）——模板与存量 app 的双向显式同步（§9）靠 doctor 让落差可见，否则"显式升级"永远没人记得做。

## 工作项

1. 检查项矩阵（§ app 条目，逐项 ✅/⚠️/❌）：

   | 检查 | 级别 | 说明 |
   |------|------|------|
   | path 存在且是 git 仓 | ❌ | registry 与磁盘一致性的底线 |
   | registry 字段与磁盘一致（name/repo/kind） | ❌ | 与 scan 共享判定逻辑（T5.2 的 Go 层复用） |
   | templateVersion vs 模板当前版 | ⚠️ | 落后 N 版报告（§9） |
   | `@innate/ui` 版本 vs verdaccio 最新 | ⚠️ | 离散度：全 app 的 ui 版本分布（§9 第 4 条） |
   | deploy.yaml 目标 ↔ workflow 文件存在 | ⚠️ | 登记了 pages 但仓里没有 deploy-pages.yml |
   | skills.yaml 条目 path 有效 | ⚠️ | 断链的 skill 登记 |
   | 构建新鲜度（可选 `--build`） | ⚠️ | 实际跑 build（慢，默认关） |

2. 基座覆盖（§9 治理遵照：base 也要被 doctor 管）：kind: base 条目检查 publishes 清单里的包在 verdaccio 可查、版本对得上。
3. 输出：终端表格（按 app 分组）+ `--json`（看板/CI 消费）+ 退出码 0/1/2（健康/有警告/有错误）。
4. registry 级检查：apps/plugins/skills/deploy 四表间引用完整（如 plugins.yaml 的 source 在核心仓存在、skills.yaml 的 app 字段在 apps.yaml 存在）。

## 产物

`innate doctor` + JSON 输出 + 退出码契约。

## 验收标准

- [ ] 真实 workspace 首跑出完整报告，与人工抽查一致（已知问题如实呈现）
- [ ] 埋雷实验：改一个 app 的 templateVersion 造落差、删一个 workflow、断一个 skill 链——三项都被抓出且级别正确
- [ ] `--json` 可被 jq 消费；退出码契约经 shell 实测
- [ ] 全绿时退出码 0（可信的绿，不误报）

## 风险与注意

- doctor 只读不修：发现的每一项附"怎么修"的一句话指引，但**不自动改**——registry 是事实源，自动修事实源等于掩盖磁盘现实。
- ui 版本查询依赖 verdaccio 在跑：服务未起时该项降级为"跳过（服务未运行）"而不是 ❌——生态里 app 不依赖 doctor 也能活。
