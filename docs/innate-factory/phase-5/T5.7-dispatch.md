# T5.7 innate dispatch（多 Agent 派发）

> Sprint: Phase 5（W4）· 状态: 未开始 · 规模: L · 前置: T5.8（看板状态模型先立）
> 设计依据：总方案 §7、[multi-agent-dispatch.md](../../solution/multi-agent-dispatch.md)（波次协议）

## 目标

`innate dispatch <T> --agent <harness> [--wave]` 把 dispatch 协议（人工纪律）变成命令：worktree 隔离 + prompt pack 组装 + headless 启动 agent + 看板状态自动流转。多 Agent 并行处理任务，全程在看板上可见。

## 背景与动机

§7.2 闭环的中段自动化：context pack（`task/project/<pkg>/`）→ dispatch → 各 agent 在各自 worktree 执行 → PR（`Closes #N`）→ merge 自动关 issue → task-watcher sync → 网站看板更新。现有人工做的是：开 worktree、拼 prompt、启动会话、改 issue 状态——四步全是机械动作，正是 CLI 的菜。协议的四条规则（§7.3：波次闸门 / 文件互斥即依赖 / agent 身份可见 / 状态汇报走 git）是本卡的行为边界，不是发明。

## 工作项

1. **worktree 隔离**：`git worktree add ../wt-<issue>-<agent> -b task/<issue>` ；任务完成后的清理命令（`innate dispatch clean`）。
2. **prompt pack 组装**：handoff + context + 任务文件（`task/issues/T*.md`）三段拼装；仓库级约定**不进 pack**（由各仓的 repo skill 承载，§8"prompt pack 因此变薄"）；pack 落盘为 worktree 内文件，agent 首个输入指向它。
3. **headless 启动**：harness 命令模板外置（workspace `.innate/harness.yaml` 或 `~/.innate/`）：

   ```yaml
   claude: claude -p --dangerously-skip-permissions "<pack 路径>"
   zcode:  zcode --headless "<pack 路径>"
   ```
   v1 实测保证 1–2 个 harness，其余模板占位。启动即后台（detach），CLI 不阻塞等 agent。
4. **看板流转**：`gh issue edit <N> --add-assignee <agent-label> --add-label in-progress`（具体形态随 T5.8 定的状态模型）；agent 产出 PR 描述自动带 `Closes #N`。
5. **`--wave` 波次闸门**：读任务包 `waves.md`，仅当上一层任务全部 merge 且集成验证绿（`innate doctor` 或任务包声明的 verify 命令）才派发下一层；不满足则打印等待原因退出。
6. **dry-run 必备**：打印将创建的 worktree 路径 / 分支名 / pack 文件清单 / issue 变更，零执行。

## 产物

`innate dispatch`（单任务 + 波次）+ harness 命令模板 + worktree 清理命令。

## 验收标准

- [ ] dry-run 输出完整计划且磁盘/GitHub 零变化
- [ ] 真跑一个样例任务（scratch repo 或本仓低风险任务）：agent 会话启动、issue 状态流转、PR 产出且带 `Closes #N`
- [ ] 双 agent 并行两个任务：worktree 互不干扰，看板两条 in-progress
- [ ] `--wave`：上层未合时拒绝派发下层并说明；合并后放行
- [ ] 波次合并遵循单写者原则提示（README/verify/interaction 由合并者维护——协议文字进命令输出）

## 风险与注意

- headless 模式各 harness 的参数与权限模型差异大且随版本变——**模板外置**是生存策略，CLI 不硬编码任何 harness 命令。
- dispatch 不做 agent 产出的质量把关：那是 verify 命令 + PR review 的事。CLI 的职责边界 = 把人从机械动作里解放，不替人判断。
- issue 状态模型必须与 T5.8 定稿一致（单一真源），两卡联动开发，先 T5.8 后本卡。
