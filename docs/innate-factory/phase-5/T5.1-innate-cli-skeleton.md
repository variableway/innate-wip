# T5.1 innate-cli Go 骨架与命令树

> Sprint: Phase 5（W1）· 状态: 未开始 · 规模: M · 前置: Phase 4

## 目标

在 `base/innate-backend/innate-go` 新增 `cmd/innate`（二进制名 **`innate`**），立起总方案 §4 的完整命令树（先全 stub），定工作区定位与版本注入机制。后续每张收编卡往树上挂真实现。

## 背景与动机

总方案 §0：innate-backend（Go + skills）是 innate-cli 落点；innate-go 已有 CLI 工程基座（`cmd/innate-go`、`internal/cli|metaapi|store`、Taskfile，`task build` → `bin/`）。**决策：新增 `cmd/innate` 而非改造 `cmd/innate-go`**——innate-go 保持"后端基座样例"身份（meta server / vine 样例），innate 是 factory 的正式工具名，二者共存于同一 module、同一 Taskfile。

## 工作项

1. `cmd/innate/main.go` + `internal/innate/`（命令注册沿用 innate-go 现有 CLI 组织方式，以实际代码为准）。
2. 命令树（§4 全景，全部 stub 注册、`--help` 可见、执行打印"未实现，python 兜底：<对应脚本>"）：

   ```
   innate new app|plugin|skill      # M2（T5.3）
   innate registry scan|clone       # M2（T5.2）
   innate npm start|stop|publish|status   # M3（T5.4）
   innate skill link                # M2 尾（T5.6）
   innate doctor                    # M3（T5.5）
   innate task import|board         # M4（T5.8）
   innate dispatch                  # M4（T5.7）
   ```
3. 工作区定位：向上查找 `registry/apps.yaml`（类 `git rev-parse`），找不到报"不在 innate workspace 内"；`--root` 可显式指定。
4. 版本注入：`-ldflags "-X main.version=$(git describe --tags)"`，`innate --version` 输出。
5. Taskfile 增补：`build:innate` / `install:innate`（复用既有 build/install 模式）。
6. README（innate-go 的 README 增一节"innate CLI"）：树、定位机制、python 兜底对照表。

## 产物

`cmd/innate` + 命令树骨架 + 工作区定位 + 版本注入 + Taskfile 目标。

## 验收标准

- [ ] `task build:innate` 产出 `bin/innate`，`innate --help` 展示全树
- [ ] 在 innate-workspace 任意子目录执行能定位到根；在外部目录报清晰错误
- [ ] 全部 stub 的兜底提示指向正确 python 脚本路径
- [ ] `innate-go` 既有命令（server / desktop-app）不受影响（回归：`task test` 绿）

## 风险与注意

- module 内两个 cmd 的依赖要分家：`internal/innate/` 独立成包，不反向 import metaapi/store——CLI 工具不该拖 server 依赖进二进制。
- go.mod 的既有 pin / replace（README 提到 vine 样例的旧 pin 问题）不要顺手清理——收编 PR 不夹带无关改动（Phase 0 纪律的延续）。
